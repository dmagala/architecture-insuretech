## Текущие проблемы архитектуры

### 1. Проблемы синхронного взаимодействия

**Проблема**: Сервисы `core-app` и `ins-comp-settlement` получают данные о продуктах через синхронные REST API вызовы к `ins-product-aggregator`.

**Риски**:
- **Каскадные сбои**: При недоступности `ins-product-aggregator` или одной из страховых компаний, все зависимые сервисы также становятся недоступными
- **Высокая задержка**: Каждый запрос к `ins-product-aggregator` требует синхронного ожидания ответа от всех 5 страховых компаний
- **Блокирующие операции**: Сервисы не могут обрабатывать другие запросы во время ожидания ответа от страховых компаний
- **Сложность масштабирования**: При росте нагрузки на страховые компании, весь процесс получения продуктов замедляется

### 2. Проблемы с локальными репликами данных

**Проблема**: Сервисы хранят локальные копии данных о продуктах и тарифах, обновляемые по расписанию.

**Риски**:
- **Неактуальные данные**: Между обновлениями (15 минут для core-app, 24 часа для ins-comp-settlement) данные могут быть устаревшими
- **Синхронизация данных**: При изменении тарифов страховых компаний, клиенты могут видеть неактуальную информацию
- **Дублирование данных**: Одинаковые данные хранятся в нескольких местах, что усложняет поддержку
- **Проблемы консистентности**: При сбоях в процессе обновления данных, сервисы могут работать с неконсистентными данными

### 3. Проблемы с обработкой ошибок

**Проблема**: Ошибки взаимодействия между сервисами приводят к сбоям в работе системы.

**Риски**:
- **Отсутствие отказоустойчивости**: Один сбой в цепочке вызовов приводит к полному отказу функциональности
- **Сложность диагностики**: При каскадных сбоях сложно определить первоначальную причину проблемы
- **Потеря данных**: При сбоях в процессе оформления страховок, данные могут быть потеряны
- **Плохой пользовательский опыт**: Клиенты получают ошибки вместо ожидаемых результатов

### 4. Проблемы масштабирования

**Проблема**: При планируемом росте до 10 страховых компаний текущая архитектура не справится с нагрузкой.

**Риски**:
- **Рост задержек**: При увеличении количества страховых компаний в 2 раза, время ответа может увеличиться в 4 раза
- **Увеличение точек отказа**: Больше страховых компаний = больше потенциальных точек отказа
- **Проблемы с ресурсами**: Синхронные вызовы ко всем компаниям будут потреблять больше ресурсов
- **Сложность мониторинга**: При росте количества интеграций усложняется отслеживание состояния системы

### 5. Проблемы с мониторингом и наблюдаемостью

**Проблема**: Отсутствие централизованного мониторинга событий и состояния системы.

**Риски**:
- **Медленное обнаружение проблем**: Команда узнает о проблемах от пользователей, а не из мониторинга
- **Сложность диагностики**: При проблемах сложно определить, какой именно сервис или интеграция вызвали сбой
- **Отсутствие метрик производительности**: Нет данных о том, какие страховые компании работают медленнее других
- **Проблемы с SLA**: Сложно контролировать соблюдение SLA с партнерами

## Риски при планируемом росте

### 1. Риски производительности
- **Деградация производительности**: При росте до 10 страховых компаний время ответа может увеличиться в 4-5 раз
- **Проблемы с памятью**: Локальные копии данных будут занимать больше места
- **Увеличение нагрузки на БД**: Частые обновления кэша будут создавать дополнительную нагрузку

### 2. Риски надежности
- **Увеличение вероятности сбоев**: Больше интеграций = больше возможностей для сбоев
- **Каскадные отказы**: При сбое одной страховой компании могут пострадать все остальные

### 3. Риски бизнеса
- **Нарушение SLA**: При росте нагрузки система может не справляться с заявленными SLA
- **Потеря клиентов**: Медленная работа системы приведет к оттоку клиентов
- **Репутационные риски**: Публичные сбои системы негативно влияют на репутацию компании
- **Финансовые потери**: Каждый час простоя стоит 500 тысяч рублей
